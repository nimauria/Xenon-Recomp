# Project Xenon CPU V2 design and migration audit

Date: 2026-09-19

## Scope and migration rule

CPU V2 evolves the existing correctness-first Xenon PPC / VMX / VMX128 static recompiler into a production native-AOT core. The existing semantic catalogue is the source of truth and is preserved. CPU V2 does **not** introduce a normal runtime guest fetch/decode/dispatch/interpreter loop, and it does not add a JIT guest decoder.

The canonical architecture remains:

```
Xbox 360 PPC / VMX128
        -> compile-time opcode frontend
        -> one Xenon semantic frontend
        -> architecture-neutral Xenon IR
        -> deterministic optimization
        -> native AOT lowering
        -> x86-64 / ARM64 host compiler
        -> native execution
```

Game modules may provide function discovery, symbols, patches and hooks. They do not own PPC, CR/XER/FPSCR, VMX/VMX128, reservation, ordering or compiled-code-dispatch semantics.

This document records the **pre-CPU-V2 baseline supplied after Memory V2 completion**. Later phases must be compared against this baseline rather than against an already-optimized intermediate tree.

## Baseline correctness gate

The supplied baseline already contains the semantic work CPU V2 must retain:

- 455 / 455 canonical opcode patterns decode.
- 455 / 455 canonical patterns lift to Xenon IR.
- 455 / 455 canonical patterns lower to native C++ AOT source.
- the generated 455-opcode corpus executes without an interpreter fallback.
- integer, control, memory, floating-point and VMX/VMX128 coverage is present.
- CR / XER / FPSCR / VSCR, LR / CTR / MSR / SPR, reservations and ordering are represented.
- the common semantic layer is architecture-neutral.
- Memory V2 already supplies `MemoryAccessContext` and executable-page generation tracking.

A clean Linux x64 Release audit build of the representative CPU/Memory targets completed successfully. The measured build subset took 17.09 seconds wall-clock and peaked at 368,924 KiB resident memory on the audit host. These numbers are audit-host measurements, not release performance claims; later benchmark phases should compare like-for-like on the same host.

## Complete CPU-system audit

### Opcode frontend / decoder

The declarative catalogue contains 455 entries and is the correct semantic source of truth. In the baseline, `Decoder::decode` scans the catalogue for every recompilation-time decode, using the primary opcode as a prefilter but still traversing the catalogue linearly. Compiler/lifter logic also relies heavily on mnemonic string comparison.

This is correct but unnecessarily expensive and weakly typed for whole-game recompilation. CPU V2 should introduce a stable generated `OpcodeId`, retain the mnemonic only for diagnostics, generate deterministic primary-opcode buckets, and validate catalogue ambiguity/specificity. Existing exhaustive decode/lift/AOT tests should remain the gate proving that every catalogue entry reaches supported IR and the backend.

### Function discovery, blocks and CFG

`StaticFunctionCompiler` currently creates essentially one IR block per guest instruction. A six-instruction loop is emitted as six labels/blocks even though only the branch/return boundaries need to terminate guest basic blocks. This prevents useful cross-instruction optimization and creates excessive labels and bookkeeping.

CPU V2 must construct guest basic blocks from function entry, branch targets, fallthrough after terminators and externally reachable entries. Blocks require explicit predecessor/successor information, branch/fallthrough edges, local call metadata and external exits. A straight-line 100-instruction sequence must normally form one block.

### Xenon IR structure and allocation behaviour

The current IR is architecture-neutral and should be evolved, not replaced. The baseline `Instruction` owns a heap-backed `std::vector<ValueId>` for operands and copies a mnemonic string into source metadata. Whole-game recompilation can create millions of nodes, so this is allocation-heavy.

The IR also lacks a production structural/type verifier and explicit side-effect metadata rich enough for safe DCE/CSE/reordering. CPU V2 needs compact common operands/source identity, CFG verification, operand/result type verification, terminator/edge validation and explicit classifications for state, memory, barriers, calls, traps, faulting operations, synchronization and control flow.

SSA should only be introduced if measurements show it materially improves the optimizer. Cross-guest-instruction optimization is mandatory; a particular SSA implementation is not.

### Optimizer

The baseline optimizer is intentionally small and primarily performs local constant folding. It does not provide broad DCE, common-subexpression elimination, architectural state promotion, redundant register read/write elimination, CFG cleanup or state-aware flag optimization.

CPU V2 should grow a deterministic pass pipeline with per-pass correctness rules and optional statistics. State promotion and redundant architectural state traffic are higher priorities than adding fashionable compiler machinery.

### CpuState traffic

The baseline generated 455-opcode source contains 1,741 textual `state.` member uses and one `state.cia = ...` assignment in each of the 455 generated single-instruction functions. In the representative six-instruction function-flow corpus, generated source contains 29 `state.` member uses, six CIA writes and twelve NIA writes.

Release assembly for `flow_loop` confirms repeated guest-state traffic around the loop, including calls to `CpuState::set_cr_field` and `CpuState::cr_bit`. GPR values are also written back and reloaded across adjacent guest instructions.

CPU V2 should promote GPR/FPR/vector/LR/CTR values and, separately and more carefully, CR/XER/FPSCR/VSCR state. Architectural state must be materialized at exits, faults, traps, syscalls, external calls, debugger checkpoints and other observable boundaries.

### Guest PC / CIA / NIA

The baseline writes CIA for every generated canonical instruction and writes CIA/NIA repeatedly in multi-instruction control-flow output. This is useful for a correctness-first implementation but expensive in hot straight-line code.

CPU V2 should preserve exact guest PC through compile-time source metadata, fault-site metadata and boundary materialization rather than unconditional per-instruction stores. Precise state at faults/exceptions remains non-negotiable.

### Memory V2 integration

The baseline already lowers ordinary memory operations through a `MemoryAccessContext`, so CPU V2 must build on Memory V2 rather than reintroducing legacy byte loops or generic dispatch.

However, every generated function currently starts with:

```
auto memory_access = memory.access_context();
```

The canonical 455-opcode generated source therefore contains 455 `access_context()` calls. Release assembly for `flow_loop` shows a vtable load/check and an indirect fallback call while acquiring the context, plus substantial setup/teardown for the read-side guard/context object.

The common RAM operations themselves can inline once the context exists. The remaining architectural target is a stable execution ABI that can carry an already-active Memory V2 access context through compiled guest calls. Slow MMIO/fault paths may still reach the owner. No global RAM mutex, ordinary-access allocation, observer callback or generic MMIO search may enter the common path.

### Branch handling and direct/indirect calls

The portable C++ backend already has useful native `goto` support for local direct branches. That should become more effective once real CFG blocks exist.

Direct guest calls, conditional link forms and indirect calls still route through `RuntimeServices::call` in generated code. Returns and non-link dynamic branches return a flow result to runtime dispatch. This is a correctness-preserving boundary but it is too expensive as the final model for statically-known common guest calls.

CPU V2 needs a compiled-function registry/linker, safe direct native guest-call linkage, and compact indirect address-to-native lookup coordinated with Memory V2 executable-page generations. Uncertain cases fall back to compiled-code dispatch, never guest interpretation.

### RuntimeServices / virtual dispatch

`RuntimeServices` remains appropriate for rare architectural/platform events such as syscalls, traps, uncommon SPR ownership and timebase. It should not be the mandatory route for common compiled control flow.

The baseline backend emits `runtime.call`, `runtime.syscall`, `runtime.trap`, `runtime.read_spr`, `runtime.write_spr` and timebase accesses where required. CPU V2 should keep rare operations behind this boundary while making common static control flow native.

### Integer lowering

Simple integer operations generally lower to direct C++ expressions and allow the host compiler to choose native arithmetic. The representative Release loop uses native add/compare instructions; the larger inefficiency is surrounding state/CR traffic rather than the arithmetic itself.

Helper calls remain for more complex carry/overflow/rotate/divide semantics. CPU V2 should inspect generated assembly before replacing them. This audit does **not** justify a hand-written x86 emitter; portable C++ AOT remains the correct primary backend and ARM64 correctness path.

### CR / XER

The baseline materializes CR/XER eagerly in several common sequences. The representative loop calls `CpuState::set_cr_field`, then calls `CpuState::cr_bit` for the immediately following conditional branch. This is a clear candidate for exact value forwarding/lazy materialization.

Any optimization must preserve partial CR fields, XER CA/OV/SO, Rc forms and all observable reads. The target is fewer round-trips, not a weaker flag model.

### VMX / VMX128

The semantic map is broad and complete, but common vector operations still collapse into `aot::execute_vector(VectorSemantic, guest_word, ...)`, which performs a runtime switch despite the guest opcode already being known during recompilation.

The generated 455-opcode canonical corpus contains **203 calls to `aot::execute_vector`**. This is the clearest baseline evidence for Phase 16.

CPU V2 should retain Xenon vector semantics above the backend while lowering common arithmetic/logical/select/compare/shuffle/permute operations to typed IR/direct host vector operations. Rare/complex operations may remain specialized helpers when that is better. The canonical semantics must never become x86 intrinsic semantics.

### Vector register liveness

The architecture exposes 128 VMX128 registers. The baseline reads/writes architectural vector state around vector operations; it does not perform broad liveness-aware vector state promotion across real guest blocks.

CPU V2 should keep live vectors in compiler temporaries/host vector registers where practical, while respecting host register pressure. It must not attempt to keep all 128 guest vector registers resident.

### Floating point / FPSCR

The current FP path deliberately prioritizes correctness. Audit finds host floating-environment operations including `fegetenv`, `fesetenv`, `feclearexcept`, `fetestexcept` and `fesetround`, plus thread-local FP bookkeeping. That is a potentially significant cost but cannot be removed blindly.

CPU V2 should measure whether one guest FP execution context can amortize host environment setup and only change host rounding when the guest FPSCR rounding mode changes. Strict FMA, NaN/signalling-NaN handling, conversions, sticky flags and `mffs`/`mcrfs`/`mtfs*` observability must remain exact. Fast-math is forbidden.

### Portable C++ AOT backend

The backend is valuable and should remain. It provides deterministic generated source, architecture neutrality, mature host optimizer use, Windows/Linux portability and the natural first ARM64 path.

The audit shows poor code around state materialization/context setup rather than evidence that C++ itself is incapable of producing good arithmetic. CPU V2 should improve generated C++/IR first and inspect final machine code after every major change. A direct machine-code emitter remains a future benchmark-driven option only.

### x86-64 backend state

There is no need to fork guest semantics into x86-specific operations. Host-specific optimization should be limited to areas where profiling later proves useful: SIMD, byte swap, permutes, lookup ABI/layout and feature variants.

The current Release assembly is useful as a quality signal, not a semantic source of truth.

### ARM64 / Android readiness

The common IR/frontend is already architecture-neutral enough to preserve as the core. CPU V2 must keep memory ordering explicit, avoid x86 flag assumptions and avoid relying on x86 TSO. Portable C++ AOT should be the first ARM64 correctness path; NEON tuning belongs below shared IR.

### Executable-page invalidation

Memory V2 and the existing `ExecutableCodeCache` already provide useful groundwork: source snapshots, executable-page generation validation and stale translation eviction. CPU V2 should integrate the future compiled-code registry with this rather than creating a second incompatible invalidation model.

There must still be no interpreter fallback when executable memory becomes stale. CPU V2 provides the invalidation/registry contract; a future dynamic native recompiler can be added separately if authorized.

### Three cores / six hardware threads

CPU state is already representable per execution context; CPU V2 must formalize the API so six independent guest hardware-thread contexts can be scheduled by the runtime. Shared reservation/ordering/timebase/interrupt ownership must be coordinated with Memory V2/runtime where architecturally required, without simulating the physical pipeline, predictors, caches or instruction timing.

### Generated source, compilation time and whole-game scaling

The baseline 455-opcode generated source is ~296 KiB and the representative six-instruction flow function is ~2.6 KiB of generated C++. One-block-per-instruction output increases labels, state materialization and compiler bookkeeping.

The clean representative target build measured 17.09 seconds and 368,924 KiB peak RSS on this audit host. Whole-game figures cannot be meaningfully claimed until a game/function-discovery corpus is fed through Xenon. Later phases should add deterministic translation-unit sharding, decoder/lifter/optimizer throughput, generated source size, host compile/link time, peak RAM and native binary-size benchmarks.

### Build configuration / compiler hardening

The repository has configure presets but no CMake build presets; builds therefore use the configured binary directory directly (`cmake --build build/linux-x64-release ...`). This is a build-system detail, not a CPU defect.

Strict warnings and multi-compiler/sanitizer validation remain required. CPU V2 must avoid C++ undefined behaviour around signed overflow, shifts, alignment, type punning, vector aliasing, FP environment, threading and atomics.

```
             |                       |
             +-----------+-----------+
                         |
                +--------+--------+
                v                 v

                |                 |
        Windows / Linux     Linux / Android
```

Memory operations:

```
optimized Xenon IR
        -> active MemoryAccessContext

```

```
known safe guest target -> native direct call/branch

dynamic guest target -> compiled-code registry -> native function pointer
```

## Non-negotiable invariants

1. No production guest opcode interpreter or runtime fetch/decode loop.
2. No semantic fork between x86-64 and ARM64.
3. Real CFG/basic-block optimization replaces one-instruction compiler granularity.
4. Common guest state should remain in compiler/host values where safe and materialize only at observable boundaries.
5. Common integer/branch/memory/vector work must not disappear behind generic runtime dispatch when direct native lowering is safe.
6. Memory V2 remains the sole owner of guest address mapping, reservation/coherency and executable-page generations.
7. Every optimization preserves architecturally observable state at exits, faults, traps, syscalls, runtime calls and synchronization boundaries.
8. The 455-opcode decode/lift/AOT/native coverage remains a mandatory gate.
9. Game modules never implement Xbox CPU semantics or compiled-code dispatch.

## Phase 1 conclusion

The existing CPU does **not** need a semantic rewrite. Its strongest assets are the complete opcode/semantic map, architecture-neutral IR, portable AOT backend and Memory V2 integration. Its primary CPU V2 weaknesses are compilation granularity, architectural-state traffic, weakly typed frontend identity, limited optimizer structure, generic vector dispatch, runtime call boundaries and FP environment cost.

The migration should therefore improve architecture *around* the proven semantics in the numbered order above. Phase 2 may begin only while the baseline correctness gate remains green.

## Phase 4 implementation decision — Xenon IR V2 verifier and representation

CPU V2 Phase 4 keeps Xenon IR architecture-neutral and adopts **block-local
single-definition values** rather than introducing function-wide SSA at this
stage. Real guest basic blocks from Phase 3 already permit optimization across
guest-instruction boundaries, while block-local values avoid premature phi-node
and merge complexity. Function-wide SSA remains an option if later profiling
shows that cross-block value propagation materially improves native code.

The IR now classifies operations conservatively with explicit effect flags for:

- architectural state reads and writes;
- guest memory reads and writes;
- barriers and synchronization;
- calls and traps;
- potentially faulting operations; and
- control flow.

The conservative classifications are intentional. In particular, current FP
operations that participate in guest status production and current VMX family
operations that may update VSCR are not marked pure merely because they return
a value. Later FP/VMX phases may refine those classifications after their
hidden status effects have been split into explicit typed operations.

A production IR verifier now runs both **before and after optimization**. It
checks block ranges, result identity, block-local definition-before-use,
fixed result types, high-value operand types, operation arity, terminator
ordering, local CFG targets and predecessor symmetry, direct constant branch
agreement with CFG metadata, guest-source metadata, and memory metadata such as
endian mode, scalar/vector widths, reservation/store-conditional widths,
vector element widths, and cache-line-zero size.

Phase 4 deliberately does not compact `Instruction::args` or source strings;
that is Phase 5 work. This separation provides a verified reference layout
before allocation/storage changes are made.

Phase 4 validation passed the full current CPU gate: 12/12 CPU tests, including
the 455-opcode canonical/lifter/AOT suite, 455 native canonical executions,
real-CFG tests, function flow, all 320 BO/CR/CTR branch matrix cases, control
boundaries, indirect branches, scalar/vector memory, integer edge cases, and
the dedicated malformed-IR/effect-model tests.

## Phase 5 implementation — compact IR representation

Phase 5 removes the two measured per-instruction ownership costs identified in
the Phase 1 audit without introducing a custom arena allocator.

`Instruction::args` is now an inline four-entry `OperandList`. The complete
455-opcode corpus proves that the current IR requires no more than four value
operands; attempts to exceed that capacity fail immediately instead of silently
allocating. This removes the heap-owned `std::vector<ValueId>` from every IR
node while retaining `size`, indexing, iteration and `clear` semantics used by
the optimizer/verifier.

Per-node `std::string guest_mnemonic` storage has also been removed. Guest
source metadata is now the compact tuple of guest address, guest instruction
word, and stable Phase-2 `OpcodeId`. Diagnostics and the portable AOT backend
resolve the mnemonic from the canonical opcode catalogue only when a mnemonic
is actually required during recompilation. The production verifier rejects
unknown source OpcodeIds.

On the measured Linux x86-64 ABI, `sizeof(ir::Instruction)` fell from **88
bytes in the Phase-1/Phase-4 layout to 64 bytes**, a 27.3% fixed-size reduction,
while also removing the operand-vector and mnemonic-string per-node dynamic
allocation opportunities. `ir::Block` remains 96 bytes; Phase 5 intentionally
does not add a bespoke arena/linear allocator without whole-game profiling.

The compact representation does not change generated guest semantics. The full
12-test CPU gate remains green, including the 455-opcode lowering/native corpus,
CFG/verifier tests, branch matrix, scalar/vector memory and integer-edge tests.

## Phase 6 implementation — architectural register promotion

Phase 6 adds conservative block-local promotion for the highest-frequency
architectural register files: GPRs, FPR bit registers, VMX/VMX128 registers,
LR and CTR. Repeated reads of a promoted register alias the existing Xenon IR
value, and writes are deferred until architectural state is actually observable.

Dirty promoted state is materialized before potentially faulting memory
operations, traps, barriers/synchronization, control-flow exits, and runtime
boundaries that may inspect mutable `CpuState`. Returning guest calls and other
runtime operations that can mutate architectural state invalidate the promoted
cache before subsequent guest instructions. This preserves precise state at
fault/exit boundaries while letting ordinary straight-line guest sequences stay
in host compiler values.

CR/XER flag forwarding is intentionally not part of this phase; it remains the
separate Phase 7 change. Likewise, promotion remains block-local rather than
introducing cross-block phi state before profiling justifies that complexity.

The dedicated acceptance corpus compiles 100 consecutive `addi r3,r3,1`
instructions into one initial `state.gpr[3]` read and one final architectural
write. Tests also verify materialization precedes a potentially faulting load,
returning guest calls invalidate cached state, and FPR/vector/LR/CTR chains are
promoted. The full CPU gate is now 13/13 tests and remains green, including all
455 canonical/native opcode checks.

## Phase 7 implementation — CR / XER flag optimization

Phase 7 extends the conservative state-promotion model to architecturally
visible integer condition state without weakening PowerPC semantics. XER CA,
OV and SO are represented as typed `I1` values in IR, with sticky-overflow
behaviour preserved explicitly. Compare results can feed a following CR branch
directly instead of forcing an immediate write/read round-trip through
`CpuState`.

Whole-XER/whole-CR reads, `mcrxr`, explicit CR/XER bit operations, runtime
boundaries, potential faults and control-flow exits still force exact canonical
materialization. `mcrxr` also invalidates the promoted XER bits after the
architectural clear. Dedicated tests cover carry chains, sticky overflow,
compare-to-branch forwarding, CR/XER observability and the clearing behaviour.

## Phase 8 implementation — deterministic optimizer V2

Phase 8 replaces the small correctness-first optimizer with a deterministic
pipeline that retains the Phase-7 state promotion and adds broader safe local
simplification. The current pipeline includes richer constant folding, copy and
algebraic simplification, comparison/select simplification, redundant
extension removal, local common-subexpression elimination, dead-code
elimination and branch simplification. Signed constant comparison folding uses
the source operand width rather than the boolean result width.

`OptimizationStats` and `OptimizationReport` expose optional diagnostics such
as constants folded, state reads eliminated, deferred/materialized state,
CSE/DCE counts and branch simplification. Diagnostics remain opt-in and do not
alter normal Release execution.

## Phase 9 implementation — Memory V2 native execution ABI

Phase 9 makes `ExecutionContext` the primary CPU V2 native-entry ABI. One
context owns references to `CpuState`, `MemoryPort`, `RuntimeServices` and an
already-active `MemoryAccessContext`, so native guest-to-guest calls can reuse
the same Memory V2 fast view instead of reacquiring a polymorphic memory
context for each guest function.

Generated common RAM loads/stores, floating/vector memory operations, LR/SC,
barriers, cache-block zero, `icbi`, string operations and partial vector memory
use `MemoryAccessContext`. Reservation operations were moved into that context
so the same Memory V2 reservation/coherency model is used by generated native
code. The legacy three-argument native function remains as a compatibility
wrapper that constructs an `ExecutionContext` once and enters the V2 function.

## Phase 10 implementation — effective-address optimization

Phase 10 introduces architecture-neutral `AddImmediate` IR for common PPC
base-plus-displacement addressing. D/DS-form RA=0 addresses become constants
directly, RA=0 indexed forms reuse RB instead of synthesizing `0 + RB`, and
redundant 32-bit address truncation before Memory V2 operations is removed.
Update forms preserve the full computed architectural effective address before
writing RA.

These transformations only simplify address formation; Memory V2 remains the
sole authority for mapping, permission, MMIO, alias and fault checks.

## Phase 11 implementation — CFG-native control flow

Phase 11 makes the Phase-3 CFG materially useful to optimization and lowering.
Constant branch conditions are simplified, unreachable local blocks can be
removed, predecessor/successor metadata is rebuilt after CFG changes, and
local direct branches/fallthrough lower to ordinary generated C++ `goto`
control flow. Static external branches leave the compiled function with a
fixed `FlowReason::Branch` result rather than entering a guest instruction
dispatch loop.

## Phase 12 implementation — proven direct guest calls

Phase 12 adds explicit `DirectCallBinding` support to the portable AOT backend.
When the recompiler/linker proves a guest call target is safe for normal native
call semantics, the generated caller invokes the target `ExecutionContext&`
entry directly. The callee must return with `FlowReason::Return` to the exact
expected guest LR; unusual control flow is propagated outward rather than
silently treated as a normal host return.

Unbound or unproven guest calls retain the existing compiled-runtime fallback.
This keeps direct linking an optimization rather than a semantic assumption.

## Phase 13 implementation — indirect compiled-code dispatch

Phase 13 extends the existing executable-code cache into the CPU V2 indirect
native registry instead of creating a parallel dispatch system. V2 entries are
registered against the same Memory V2 executable-page snapshots used by the
legacy cache and can be bound to an `ExecutionContext` through a non-virtual
lookup callback.

The registry now has a 256-entry direct-mapped hot cache for single-page native
entries. A hot hit still validates the current physical executable-page
identity and generation through the active `MemoryAccessContext`; misses,
collisions, multi-page translations and stale entries fall back to the
authoritative shared registry. SMC, alias writes, protection changes, `icbi`,
unmap/remap and explicit invalidation therefore cannot enter stale native code.

Indirect branch and indirect call lookup are separate contracts. Any current V2
entry may satisfy an indirect branch/tail-dispatch lookup. An indirect call may
bypass `RuntimeServices::call` only when its registry entry is explicitly
marked `direct_call_safe`, meaning the compiler/linker has proven normal LR
return behaviour. This prevents unusual guest call/return shapes from being
misrepresented as host calls.

Generated `bcctr` can now tail-dispatch directly to a native V2 entry, while
`bcctrl`/other indirect call forms can directly invoke a call-safe native entry
and validate the expected LR return. Lookup miss retains the existing compiled
runtime boundary; no interpreter or runtime guest decoder is introduced.

The Phase 7–13 completion gate passes 25/25 selected CPU + Memory V2 tests,
including the 455-opcode generated native corpus, CFG/IR/state/optimizer tests,
direct and indirect control-flow tests, scalar/vector memory tests, integer
edge cases, Memory V2 ordering/hardening/type/fault tests and executable-code
cache generation/SMC tests.

## Phase 14 implementation — guest-PC boundary materialization

Generated native code tracks the current guest instruction from IR source
metadata. It writes CIA/NIA before operations marked as potentially faulting,
calling into runtime code, trapping, changing control flow, or synchronizing;
straight-line arithmetic and state updates do not write the guest PC per
instruction. Normal block exits materialize the final CIA and next NIA.
This preserves the PC observed by memory faults, syscalls, traps, runtime
callbacks and dispatcher exits without introducing a second PC map or a guest
interpreter. The optimization is deliberately conservative: effect metadata
determines the boundary, so new IR operations that can fault or expose state
must carry the appropriate effect flag.

The 100-instruction straight-line CFG fixture now has one CIA write rather
than 100. A generated native load-fault fixture verifies CIA/NIA identify the
faulting instruction and that the following guest instruction does not execute.
The Windows Release CPU gate passes 13/13 tests, including the generated
455-opcode corpus. Phase 15 integer lowering is next; Phase 14 does not claim
to provide asynchronous debugger sampling inside uninterrupted native code.

## Phase 15–16 progress — measured native lowering

The Windows x64 Release disassembly showed that ordinary integer shifts were
already folded to native shifts, so their portable helper remains unchanged.
It also exposed an out-of-line `set_xer_ca` call in a generated `addc` hot path.
Small XER and CR0 field operations now live inline with `CpuState`, with their
old out-of-line definitions removed. The rebuilt `addc` body has no helper call
or stack frame, and the integer-edge tests still pass. This is a targeted
Phase 15 improvement, not a complete audit of every integer opcode or host.

For Phase 16, VMX/VMX128 AND, AND-complement, OR, XOR and NOR now lower to a
compile-time-selected portable bitwise operation. The shared semantics use
two 64-bit chunks; byte order is irrelevant for these bitwise operations.
The existing runtime semantic path reuses the same implementation. `vnor`
and `vnor128` also lift to one binary IR operation instead of a redundant
OR-plus-NOT pair. Windows x64 Release disassembly of generated `vnor` shows
SIMD OR/NOT instructions and no runtime semantic switch. Native smoke tests
exercise all five VMX operations and VMX128 AND/NOR. Other vector families
still use the generic semantic path and remain Phase 16 work.

## Phase 16 progress — native vector lowering

Native inline templates added for common VMX/VMX128 operations:
- **Splat**: byte/halfword/word register and immediate forms
- **Modular arithmetic**: `vector_add_modular<T>`, `vector_sub_modular<T>` for byte/halfword/word lanes

Templates parameterized by lane type enable compile-time specialization. Runtime `execute_vector` dispatch remains for saturating/averaging/comparison/shift/permute operations until profiling justifies per-operation templates.
