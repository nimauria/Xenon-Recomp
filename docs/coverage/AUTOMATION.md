# Coverage refresh automation

The README dashboard (`summary.svg`, `dashboard.svg`) and the coverage reports are regenerated by `.github/workflows/coverage-refresh.yml`. Nobody needs to edit SVGs or recalculate percentages by hand. The workflow builds nothing. It reads source files, the reviewed manifest and CTest results that the Windows and Linux workflows have already produced.

## Triggers

| Event | What is inspected |
| --- | --- |
| Push to `development-restructure` touching coverage inputs (kernel export sources, PPC decoder/lifter/fallback, Xenos shader and PM4 sources, `include/xenon/gpu/`, `tests/`, `tools/coverage/`, `docs/coverage/`) | The pushed commit. The job waits up to 120 minutes for that commit's Windows/Linux runs. |
| Weekly schedule (Monday 05:23 UTC) | The head of `development-restructure` |
| Manual `workflow_dispatch` | The head of `development-restructure` (the wait time is an input) |

GitHub runs scheduled events from the copy of the workflow on the **default branch** (`main`). The jobs never rely on that branch's code. They check out `development-restructure` explicitly (`COVERAGE_TARGET_BRANCH`), and `refresh.py target` rejects any other push branch and every pull-request event. **The weekly schedule only fires once this workflow file also exists on the default branch.** Until then, use pushes or manual runs.

## Steps

The `audit` job runs with `contents: read` and `actions: read`, and does not persist checkout credentials.

1. Checks out the target revision and confirms it (`refresh.py target`).
2. Runs the coverage tooling tests (`python3 -m unittest discover -s tools/coverage`).
3. Validates the source inventories and the manifest in strict mode (`generate.py --validate`).
4. Reads existing CTest results (`collect_ci_evidence.py`). It uses the `ctest-results-<platform>` JUnit artifact when present, otherwise the CTest lines in the job log. Results the script cannot read are recorded as unavailable, never as passing.
5. Regenerates both SVGs, `REPORT.md`, `KERNEL_REFERENCE.md`, `inventory.json`, `audit-candidates.json` and `AUDIT.md`, then compares them with the committed snapshot (`refresh.py run`). The comparison lists added, removed and renamed operations (renames are matched by ordinal, opcode pattern or enum value), changed implementation paths, changed test evidence, new or altered stubs and partials, classification and displayed-state changes, previously verified operations that lost verification, and new or resolved candidates and problems.
6. Packages the generated-file changes as a patch (`refresh.py patch`). It fails if anything outside `docs/coverage/` generated files changed.
7. Uploads the reports (`diff.json`, `diff.md`, `pr-body.md`, `summary.md`, `status.json`, `ci-evidence.json`, `proposal.patch`) and writes a job summary.

The `propose` job runs only if `audit` succeeded with no validation errors. It runs with `contents: write` and `pull-requests: write`, and executes only code from the already-checked `development-restructure` commit. It never runs pull-request code.

- When files changed, it commits them to `bot/coverage-refresh` and opens or updates one pull request into `development-restructure`. The findings go in the PR description.
- When nothing changed, it closes an open bot pull request that has become obsolete.

## Safety rules

- **Generated files only.** A proposal can only change the seven generated files in `docs/coverage/`. It cannot change `coverage.json`, runtime sources, tests or workflows.
- **No force-push.** Updates are fast-forward commits on top of the current bot branch head, merging in the new base revision when needed. The script refuses any forced push.
- **Developer commits are respected.** If anyone other than the bot has pushed to `bot/coverage-refresh`, the workflow leaves the branch and its pull request untouched and reports why.
- **No loops.** The bot pushes with `GITHUB_TOKEN`, which does not trigger workflows, and only to its own branch. Merging its pull request re-runs the refresh. That run proposes nothing unless the sources or CI results changed in the meantime, and it converges: each run either finds no change or applies the latest one.
- **Deterministic output.** Files contain a content digest. When a new revision produces the same content, the earlier assessed commit SHA is kept, so a repeat run produces byte-identical files and no commit. The SHA is renewed when content changes, or when fresh same-commit CI evidence replaces evidence that was stale.

## Automatic versus human-approved

| Updated automatically (bot pull request, merged by a maintainer) | Requires human approval (an edit to `tools/coverage/coverage.json`) |
| --- | --- |
| Listed counts from source-declared inventories | Any new classification (`verified`, `implemented_unverified`, `partial`, `stub`, `unimplemented`) |
| Per-area and per-state counts, percentages and SVGs | Acting on any audit candidate |
| Showing a reviewed `verified` entry as implemented, unverified while its CTest target is failing, missing or skipped, and as verified again once it passes | Resolving a `classification_conflict` |
| Audit candidates, validation problems and the revision diff | Fixing a broken test or implementation reference |
| Assessed-commit and CI-evidence metadata | Updating the pinned kernel reference snapshot |

## Relationship to Overall CI

`ci.yml`'s `coverage-dashboard` job still runs the tooling tests and `generate.py --check`, and still fails when the dashboard content (SVG cells, counts, `REPORT.md`, `KERNEL_REFERENCE.md`) is stale or the manifest is invalid. It does not query the network. It reuses the CI evidence recorded in `inventory.json`. Drift that is confined to the audit records, or to the assessed-revision line, is reported as a warning, because the refresh workflow proposes it. The refresh workflow never reports runtime tests as passing unless it read their actual results, and it does not filter or rerun any test, including the intermittent threading test.

The two platform workflows have one extra step: they upload `ctest-results.xml` as `ctest-results-linux` / `ctest-results-windows` (30-day retention). Their build, test and failure behaviour is unchanged.

## Running locally

```sh
python3 -m unittest discover -s tools/coverage -p 'test_*.py'
python3 tools/coverage/generate.py --validate            # strict validation, writes nothing
GH_TOKEN=$(gh auth token) python3 tools/coverage/collect_ci_evidence.py \
  --repository nimauria/Xenon-Recomp --branch development-restructure \
  --sha "$(git rev-parse HEAD)" --out /tmp/ci-evidence.json
python3 tools/coverage/generate.py --ci-evidence /tmp/ci-evidence.json   # regenerate
python3 tools/coverage/generate.py --check                # what Overall CI runs
```

Without `--ci-evidence`, the generator reuses the outcomes recorded in `inventory.json`. A local run records `git rev-parse HEAD` as the assessed revision, and marks it `+`/"with uncommitted changes" when `src/`, `include/`, `tests/` or the manifest have uncommitted edits.

## Repository settings

For the bot to open pull requests, **Settings → Actions → General → Workflow permissions** must allow "Allow GitHub Actions to create and approve pull requests". If it does not, the `propose` job fails with the API's error after pushing `bot/coverage-refresh`, and a maintainer can open the pull request from that branch by hand.
